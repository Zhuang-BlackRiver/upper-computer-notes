# W3 · 实时数据到界面（ScottPlot + 线程模型）

**时间预算**：2 天 × 2 小时
**参考项目**：[ScottPlot](https://github.com/ScottPlot/ScottPlot)（MIT，.NET 绘图库，WinForms/WPF/Avalonia/Blazor 全支持）
**本周要回答的问题**：为什么你的曲线一开就卡？为什么点了"开始采集"界面就假死？

> 一周只解决两件事：**渲染怎么快**、**线程怎么不打架**。这两件事解决完，"万点实时曲线"就是水到渠成的结果，而不是靠调参碰运气。

---

## 1. 先承认一个事实：卡的不是绘制，是你

上位机曲线卡的典型现场，按出现频率排：

| 现象 | 真正原因 | 占比 |
|---|---|---|
| 曲线越跑越慢，最后卡死 | 数据点**只增不减**，缓冲区无限增长 | 最高 |
| 界面每秒抖一下 | 每来一个点就 `Invalidate()` 重绘一次 | 高 |
| 点"开始"就假死 | 采集跑在 UI 线程，或 `Thread.Sleep` 在 UI 线程 | 高 |
| 数据到了界面但不更新 | 跨线程更新控件抛异常被吞，或忘了 `Refresh` | 中 |
| 内存缓慢上涨 | 每个点 new 一个对象，事件订阅没退订 | 中 |

**换库治不了前三条。** 所以本周的顺序是：先定线程模型和数据缓冲，再选渲染库。

## 2. 线程模型：三段式，别让任何一段跨到 UI 线程

```
[采集线程/任务]                [环形缓冲]                 [UI 线程]
 轮询 PLC                    固定长度数组               Timer (30~50ms)
 解析成 double[]   ──写──▶   或 Channel<double[]>  ──读──▶ 取最新快照
 时间戳                                                      → 更新曲线数据
                                                             → Refresh()
```

三条硬规则：

1. **采集线程绝不碰控件**。哪怕只是 `label.Text = ...`，也会在设备慢的时候把 UI 卡住（跨线程 `Invoke` 是同步等待）。
2. **UI 刷新用固定频率定时器（30~50ms，即 20~30 FPS），不是"来一个点刷一次"**。人眼分辨不出 60FPS 以上，刷得越勤越浪费。
3. **缓冲区定长**。滚动显示只需要"最近 N 秒"，N 由时间窗决定，不由数据量决定。

伪代码（`System.Windows.Forms.Timer` 或 WPF `DispatcherTimer`，间隔 40ms）：

```csharp
// 采集侧：只写缓冲，不碰界面
void OnSample(double value)
{
    _ring.Write(value);          // 定长环形缓冲，写满自动覆盖最旧
}

// UI 侧：固定 25 FPS 拉取快照
void UiTimer_Tick(object sender, EventArgs e)
{
    var snapshot = _ring.Snapshot();          // 一次拷贝，避免边写边读
    formsPlot1.Plot.Add.SignalXY(xs, snapshot);  // 或更新已有 plottable 的 Ys
    formsPlot1.Refresh();
}
```

> ScottPlot 5 自带 `DataStreamer`（数据流器）与 `DataLogger`，就是干"定长滚动"这件事的，签名以 [Cookbook 5.0](https://scottplot.net/cookbook/5.0/) 为准。**注意 v4 与 v5 API 完全不同**（v4 是 `plt.Plot.Add*`），网上大量中文教程还是 v4，抄之前先看版本。

## 3. 数据抽稀：100 万点画在 800 像素上，是浪费

屏幕宽 800px，你喂 100 万个点，**有 99.9% 的点落在同一列像素上**。抽稀不是精度损失，是把"看不见的信息"提前扔掉。

三种手段，按性价比排：

| 手段 | 做法 | 适用 |
|---|---|---|
| **时间窗截断** | 只保留最近 60s | 必做，最有效 |
| **像素级抽稀（min/max）** | 每像素列取该列内的最大最小值两个点 | 波形要保留毛刺时必用；单纯降采样会把尖峰抹掉，**这在振动/电流监测里是致命的** |
| **LTTB 降采样** | Largest-Triangle-Three-Buckets，保形降采样 | 数据要存档再回放时 |

**min/max 抽稀是最容易讲出彩的一条**：平均降采样会让一个 1ms 的电流尖峰消失，客户看到的曲线是"平稳"的，而实际设备已经异常。**保形抽稀 = 保住了这个尖峰。**

```csharp
// 每像素列保留 min 与 max 两个点（伪代码）
for (int px = 0; px < width; px++)
{
    var (min, max) = ScanColumn(px);       // 该列内所有样本的极值
    yield return (px, min);
    yield return (px, max);
}
```

## 4. 为什么是 ScottPlot 而不是 Chart / LiveCharts

| 方案 | 万点表现 | 说明 |
|---|---|---|
| `System.Windows.Forms.DataVisualization.Charting` | 卡 | 每点一个 `DataPoint` 对象，GC 压力巨大；微软已停止维护 |
| LiveCharts2 | 中 | 动画/交互漂亮，但动画本身就是开销，工业场景不需要 |
| **ScottPlot** | 好 | 面向"大数据数组"，`double[]` 直传渲染，无逐点对象；支持 `SignalXY` 按 X 均匀采样优化 |
| 自绘 GDI+ / Direct2D | 最好 | 但要自己处理坐标轴、缩放、游标——除非有特殊需求，不值得 |

**关键差异是数据模型**：ScottPlot 吃 `double[]`（连续内存），Chart 吃 `List<DataPoint>`（对象图）。前者渲染时是一段 memcpy，后者要遍历指针。这就是"同样 10 万点，一个丝滑一个卡"的根因。

## 5. 交付前必须自查的四条

1. **连续跑 8 小时**，看内存曲线是否平稳（`dotnet-counters` 或任务管理器）。上涨 = 泄漏，通常是事件没退订或缓冲没定长。
2. **拔网线**：断线重连后曲线是否恢复，还是从此空白直到重启。
3. **切到别的窗口再切回来**（后台渲染）：是否会一次性把积压的几十万点全画出来导致卡顿。应该在 `VisibleChanged` 时清空/跳过积压。
4. **高 DPI 缩放 150%**：坐标轴文字是否糊、曲线是否错位。

> 这四条写进交付清单，比"曲线很好看"值钱得多。

## 自测题

1. 为什么 UI 刷新要用固定 30~50ms 定时器，而不是"每采集到一个点就刷"？
2. 平均降采样（每 10 个点取平均）在什么场景下会造成严重后果？
3. 环形缓冲为什么比 `List<double>` + `RemoveAt(0)` 快？
4. 采集线程里直接 `label.Text = value` 会有什么问题（即使能跑通）？
5. 客户说"曲线卡"，你先看哪三个指标？

<details>
<summary>参考答案</summary>

1. 刷新是"重绘整屏"，成本与点数×频率成正比；人类感知上限约 30FPS，更高频刷新只是烧 CPU。且来点即刷会让刷新频率被设备速度绑架——设备一快就卡。
2. 振动、电流、压力冲击等含尖峰信号。1ms 的冲击被平均掉后曲线"看起来正常"，掩盖真实故障。要用 min/max 保形抽稀。
3. `RemoveAt(0)` 是 O(n) 内存搬移（10 万点每次搬 80 万字节），环形缓冲是 O(1) 覆盖写 + 两个索引。滚动窗口下这个差异是决定性的。
4. ①跨线程访问控件在 .NET Framework 上可能抛 `InvalidOperationException`，也可能"看起来正常"但埋雷；②若用 `Invoke` 同步等待，UI 繁忙时采集线程被阻塞，采样周期抖动，测出来的时间戳全错。
5. ①缓冲长度是否随时间增长（内存/点数）②UI 刷新间隔与实际帧率 ③采样线程与 UI 线程的 CPU 占比，判断是"数据太多"还是"刷得太勤"。
</details>
