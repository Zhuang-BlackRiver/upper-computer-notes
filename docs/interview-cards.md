# 面试卡片

> 每周最多产出 2~3 张。一张卡片 = 一条**能讲 3 分钟、带有具体数字或权衡**的技术决策。
> 不是"我读过 XX 项目"，而是"我在 XX 里发现了一个问题，我的做法是……，代价是……"。

## 卡片格式

```
### 标题（一句话结论）
- 场景：什么情况下会遇到
- 问题：不这么做会怎样（要有数字/故障现象）
- 做法：具体怎么做
- 代价：这个选择的缺点（必须有，否则像背稿）
- 追问预判：面试官最可能问什么，怎么答
```

## #1 上位机的性能瓶颈在往返，不在运算

- **场景**：200 个测点、Modbus TCP、往返 30ms。
- **问题**：逐点轮询一轮 = 200 × 30ms = 6 秒，刷新频率根本上不去，操作员看到的是"迟钝的界面"。
- **做法**：按（功能码, 站号）分组 → 区间合并 → 单区间不超过 121 个寄存器（125 上限 − 4，给 64 位类型留余量）→ 一次读回整段再切值。200 点压到 3~4 帧，一轮约 100ms。
- **代价**：会多读回中间"不关心"的地址（用带宽换往返）；地址表稀疏且跨度很大时收益下降，需要 `maxGap` 阈值控制。
- **追问预判**：
  - "121 为什么不是 125？" → 64 位类型占 4 个寄存器，按 125 切会把跨界值劈成两半。
  - "空地址太多怎么办？" → 设最大间隔阈值，超过就不合并，宁可多一帧。

## #2 通讯失败不该是异常，应该是返回值

- **场景**：现场断网、PLC 断电、网线被叉车压断——每天都会发生。
- **问题**：`try/catch` + 抛异常穿过通讯层到界面，界面每处都要 catch，漏一处就崩；而且异常里没有报文，现场无法判责。
- **做法**：统一 `Result` / `Result<T>`：`IsSucceed` + `Err` + `ErrCode` + **请求报文 + 响应报文 + 耗时**。错误逐层累积成 `ErrList`，保留完整链条。
- **代价**：调用处必须检查 `IsSucceed`，漏检不会编译报错（不像异常会被强制处理），要靠 code review 和封装兜底。
- **追问预判**：
  - "那真正的程序 bug 怎么办？" → 参数非法、空引用这类**程序错误仍然抛异常**；只有通讯/设备类"预期内的失败"走 Result。
  - "报文存内存不占空间吗？" → 只保留最近一次，长度几十字节。

## #3 设备状态要三态，不要一个 bool

- **场景**：一台设备 50 个测点，48 个正常、2 个读不到。
- **问题**：用 `bool Connected` 只能表达"在线/离线"，48/50 的情况被判成离线 → 运维去现场重启设备、换网线，全是无用功，真正原因是地址配错了。
- **做法**：`Online`（全部正常）/ `Warning`（部分测点异常）/ `Offline`（整台不通）。每态对应不同处置动作，并且日志里能区分"通讯失败"与"地址非法"。
- **代价**：状态判断要多遍历一遍测点集合，且 `Warning` 的阈值需要和甲方约定（比如允许 3 个坏点不报警）。
- **追问预判**："Warning 会不会太吵？" → 加去抖：连续 N 轮异常才升级状态，恢复同理。

## #4 平台和库的区别：改动文件数

- **场景**：第 7 个 PLC 品牌要接入。
- **问题**：`switch + 枚举 + 适配器` 三处改动 + 重新编译主程序 = 一次发版；客户现场装的是旧版主程序，驱动装不上。
- **做法**：`[DeviceDriver("key")]` 特性 + 反射扫描 `drivers/*.Driver.dll` + 独立 `Contract` 程序集锁版本。新品牌只新增一个类库，丢进目录即可。
- **代价**：失去编译期检查（key 写错只能运行时发现）、调试变复杂、必须处理程序集加载与版本兼容。
- **追问预判**：
  - "DLL 被锁怎么热更新？" → 独立 AppDomain（.NET Framework）或 AssemblyLoadContext 加载，卸载再覆盖。
  - "驱动版本不兼容怎么办？" → Contract 程序集版本号锁定，驱动声明所需 Contract 版本，加载时校验。

## #5 曲线保形抽稀

- **场景**：800px 宽的控件要显示 10 万个采样点。
- **问题**：99.9% 的点落在同一像素列，白画；平均降采样会把 1ms 的电流尖峰抹平，客户看到"平稳曲线"，实际设备已异常。
- **做法**：时间窗截断（只留最近 60s）+ 像素列 min/max 抽稀（每列保留极值两点）+ 固定 25FPS 刷新。
- **代价**：min/max 会让同一列出现"上下跳动"的视觉厚度；点数少了但 CPU 花在扫描列上，极大数据量需要预聚合。
- **追问预判**："为什么不用 LTTB？" → LTTB 保形更好但计算量大于 min/max，实时滚动场景 min/max 足够且更便宜；存档回放才用 LTTB。
